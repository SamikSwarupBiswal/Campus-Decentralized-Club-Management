You are a senior Product Manager, Blockchain Architect, and Full-Stack Engineer.

Create a complete, implementation-ready Product Requirements Document (PRD) for the following project:

PROJECT NAME:
Campus DAO — Decentralized College Club Management System

IMPORTANT CONTEXT:
This is a college academic project. The goal is NOT to create a new blockchain and NOT to create a cryptocurrency payment application.

We are building a web-based decentralized application (dApp) for managing college clubs, with blockchain used selectively as a trust, governance, verification, and audit layer.

The project must use ZERO-COST / FREE technologies, free tiers, open-source software, and Ethereum-compatible TESTNET infrastructure wherever possible. Do not recommend paid services unless there is absolutely no free alternative, and clearly mark any unavoidable limitation.

CORE PROBLEM:
Traditional college club management is heavily dependent on centralized databases and administrators. This can create problems such as:
- Lack of transparency in club elections
- Possibility of duplicate/manipulated voting
- Lack of transparency in governance decisions
- Unclear treasury approval history
- Difficulty independently verifying important records
- Centralized control over critical data
- Students having to trust administrators for important club decisions

CORE SOLUTION:
Build Campus DAO as a hybrid application:

OFF-CHAIN:
- React + Vite frontend
- Tailwind CSS
- Supabase for authentication and normal application data
- Club profiles
- Student profiles
- Events
- Non-sensitive application data
- Other data that does not need blockchain-level immutability

ON-CHAIN:
- Solidity smart contracts
- Ethereum-compatible testnet
- Voting
- Governance proposals
- Governance approval results
- Treasury governance / spending approvals
- Selected record verification proofs / hashes
- Blockchain transaction history

BLOCKCHAIN CLARIFICATION:
We are NOT creating our own blockchain.
We are deploying our own Solidity smart contracts on an existing Ethereum-compatible testnet.

The architecture should be:

Student
↓
React Frontend
↓
Ethers.js
↓
MetaMask
↓
Solidity Smart Contracts
↓
Ethereum-Compatible Testnet
↓
Blockchain

And for normal data:

React
↓
Supabase

WALLET / IDENTITY REQUIREMENT:
Do NOT assume that one wallet automatically equals one student.

A student can create multiple MetaMask wallets, so the system must include a student verification and wallet authorization mechanism.

Recommended flow:

College Student
↓
College identity verification
↓
Institutional email / OTP or equivalent verification
↓
Student verified
↓
Connect MetaMask
↓
Wallet address linked to verified student
↓
Wallet authorized for governance

The smart contract should only allow authorized wallet addresses to perform governance actions.

Include a wallet replacement/recovery mechanism with:
- Re-verification
- Revocation of previous wallet
- Authorization of new wallet
- Protection against changing wallets to vote twice in the same election

Clearly explain the limitation that blockchain cannot prevent a person from creating multiple wallets. Instead, the application prevents unauthorized wallets from participating.

META MASK:
Explain MetaMask as:
- Blockchain wallet
- Public wallet address management
- Transaction signing
- Private key protection
- User authorization

The private key must NEVER be stored in Supabase, React, backend servers, or exposed to the application.

ETHERS.JS:
Use Ethers.js as the communication layer between:
React frontend
→ MetaMask
→ Ethereum testnet
→ Smart contracts

SMART CONTRACT DEVELOPMENT:
Use Solidity.

Use Hardhat for:
- Contract development
- Compilation
- Testing
- Deployment

Remix may be mentioned as an optional learning/prototyping tool, but Hardhat should be the primary development workflow.

TESTNET:
Use an Ethereum-compatible testnet suitable for free academic development.

The PRD must explain:
- What Ethereum is
- What a testnet is
- Why a testnet is used
- Why real ETH is not required
- How testnet assets are obtained through faucets where applicable
- Difference between mainnet and testnet

Do NOT design the project as a cryptocurrency payment system for real college money.

The actual Indian Rupee college funds remain in existing banking/UPI/college finance systems.

ATTENDANCE / RECORD VERIFICATION:
Do not store sensitive student information directly on a public blockchain.

Recommended architecture:

Detailed attendance data
↓
Supabase/off-chain
↓
Generate cryptographic hash / verification proof
↓
Store proof/reference on blockchain

Later:

Current record
↓
Recalculate hash/proof
↓
Compare with blockchain proof
↓
Match = no detected modification
Different = possible modification

Clearly explain:
Blockchain does NOT prove that the original attendance record was truthful.
It only helps make an accepted record tamper-evident / verifiable.

- Student identity information
